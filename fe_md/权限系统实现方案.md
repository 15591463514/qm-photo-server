## 实现方案详细设计

### 一、后端权限验证流程

```
请求
  ↓
JwtAuthGuard（身份验证）
  ↓
RoleAuthGuard（角色验证，可选）
  ↓
PermissionAuthGuard（权限验证，可选）
  ↓
Controller（业务逻辑）
```

### 二、权限验证逻辑

#### 1. 角色验证（RoleAuthGuard）

**逻辑：**
- 如果接口没有 `@Roles()` 装饰器，直接放行
- 如果有装饰器，检查用户角色是否包含所需角色
- OR 逻辑：只要有一个角色匹配即可

**示例：**
```typescript
@Roles('admin', 'user')  // 用户拥有 admin 或 user 角色即可访问
```

#### 2. 权限验证（PermissionAuthGuard）

**逻辑：**
- 如果接口没有 `@RequiresPermissions()` 装饰器，直接放行
- 如果有装饰器，检查用户权限列表
- 支持 AND/OR 逻辑
- 超级管理员（R_SUPER）拥有所有权限

**示例：**
```typescript
// AND 逻辑：需要同时拥有两个权限
@RequiresPermissions('user:add', 'user:edit')

// OR 逻辑：需要拥有其中一个权限
@RequiresPermissions(['user:add', 'user:edit'], 'OR')
```

### 三、权限数据结构

#### 1. 用户权限缓存（Redis）

**Key 格式：**
```
user:permissions:{userId}
```

**Value 格式：**
```json
{
  "userId": 1,
  "roles": ["admin", "user"],
  "menus": [
    {
      "id": 1,
      "path": "/system/user",
      "name": "User",
      "title": "用户管理",
      "children": []
    }
  ],
  "buttons": [
    "user:add",
    "user:edit",
    "user:delete",
    "role:add"
  ]
}
```

**缓存时间：** 7天

#### 2. 角色权限分配接口参数

**请求格式：**
```typescript
{
  menuIds: number[],      // 菜单ID数组
  buttonIds: number[]     // 按钮ID数组（可选）
}
```

**说明：**
- `menuIds`：角色可以访问的菜单列表
- `buttonIds`：角色可以操作的按钮权限列表
- 如果只传 `menuIds`，表示该角色可以访问这些菜单，但不一定有按钮权限
- 如果传了 `buttonIds`，表示该角色拥有这些按钮的操作权限

#### 3. 权限标识格式

**菜单权限：**
- 通过 `RoleMenu` 表控制
- 用户有菜单权限才能访问该路由

**按钮权限：**
- 格式：`{menuName}:{action}`
- 示例：
  - `user:add` - 用户新增
  - `user:edit` - 用户编辑
  - `user:delete` - 用户删除
  - `menu:auth:add` - 菜单权限新增
  - `dict:type:edit` - 字典类型编辑

## 关键技术点

### 一、权限缓存策略

#### 1. 缓存结构

**用户权限缓存：**
- Key: `user:permissions:{userId}`
- Value: JSON 格式的权限数据
- TTL: 7天

**用户信息缓存：**
- Key: `user:info:{userId}`
- Value: JSON 格式的用户信息（包含权限）
- TTL: 7天

#### 2. 缓存更新策略

**权限变更时：**
1. 角色权限变更 → 清除相关用户的权限缓存
2. 用户角色变更 → 清除该用户的权限缓存
3. 菜单/按钮变更 → 清除所有用户的权限缓存（可选，或延迟更新）

**缓存失效处理：**
- 缓存未命中时，从数据库查询
- 查询后重新缓存
- 支持手动清除缓存

### 二、权限验证性能

#### 1. 查询优化

**优先从 Redis 读取：**
- 登录时加载权限到 Redis
- 权限验证时优先从 Redis 读取
- Redis 未命中时查询数据库

**批量查询优化：**
- 一次性查询用户所有权限
- 避免多次数据库查询
- 使用 Prisma 的 `include` 优化关联查询

#### 2. 缓存预热

**登录时预热：**
- 登录成功后立即加载权限
- 存储到 Redis
- 设置合理的过期时间

### 三、超级管理员处理

#### 1. 超级管理员角色

**定义：**
- 角色编码：`R_SUPER`
- 拥有所有权限
- 不受权限限制

#### 2. 权限守卫特殊处理

**逻辑：**
```typescript
// 如果是超级管理员，直接放行
if (user.roles.includes('R_SUPER')) {
  return true;
}

// 否则检查权限
return checkPermissions(user, requiredPermissions);
```

## 总结

### 核心要点

1. **权限模型：** RBAC（基于角色的访问控制）+ 细粒度按钮权限
2. **权限验证：** 后端守卫 + 前端指令双重验证
3. **权限缓存：** Redis 缓存用户权限，提升性能
4. **权限格式：** `{menuName}:{action}` 格式的权限标识
5. **超级管理员：** 特殊角色，拥有所有权限

### 实施优先级

1. **高优先级：** 后端权限核心功能、登录权限加载
2. **中优先级：** 前端权限集成、角色权限管理
3. **低优先级：** 测试优化、文档完善

### 注意事项
